# ยืนยันส่ง LINE แล้ว แต่ตารางยังขึ้น "ยังไม่ส่งใหม่" จนกว่าจะโหลดหน้าใหม่

## อาการ

แก้ใบสั่งซื้อที่ส่งไปแล้ว (ได้ Rev.1) แล้วส่งให้ผู้ขายใหม่ผ่านขั้นตอนส่ง LINE
กด "ส่งแล้ว" ระบบขึ้น **"ส่งครบทุกรายแล้ว"** ปิดหน้าต่าง

แถวในตารางยังขึ้นป้าย **"แก้ไขแล้ว — ยังไม่ส่งใหม่"** อยู่เหมือนเดิม

ออกจากหน้าแล้วเข้าใหม่ ป้ายถึงเปลี่ยนเป็น "ส่งเข้า LINE แล้ว" ซึ่งเป็นค่าที่ถูก

**หน้าจอขัดแย้งกับตัวเองในจังหวะเดียวกัน** — บอกว่าส่งครบแล้ว พร้อมกับบอกว่ายังไม่ได้ส่ง

## ที่คาดว่าจะเป็น

กดยืนยันว่าส่งแล้ว ป้ายเปลี่ยนทันที เพราะระบบเพิ่งบอกเองว่าส่งสำเร็จ

## ทำซ้ำได้โดย

1. มีใบสั่งซื้อสถานะ "สั่งแล้ว" ที่เคยส่ง LINE ไปแล้ว
2. กด "แก้ไข" เปลี่ยนจำนวน ใส่เหตุผล แล้วบันทึก — ใบขึ้น Rev.1 และป้าย "แก้ไขแล้ว — ยังไม่ส่งใหม่"
3. กด "ส่ง LINE" ที่แถวนั้น เดินจนจบแล้วกด "ส่งแล้ว"
4. ปิดหน้าต่าง **โดยไม่โหลดหน้าใหม่**

ป้ายยังเป็น "แก้ไขแล้ว — ยังไม่ส่งใหม่"

## ต้นเหตุ — พบแล้ว ไม่ต้องเดา

`src/pages/purchase/SendWizard.tsx` ใน `record()`:

```ts
await setShareStatus(order.id, status, { id: user.id, name: user.name }, version)
if (status === 'sent' || status === 'skipped') doneHere.current.add(order.id)
await onStatus({ ...order, shareStatus: status })
```

`setShareStatus()` ใน `src/services/purchaseOrders.ts:330` เขียน `sentAt = now` ลงเอกสารจริง
แต่ประกาศคืนค่าเป็น `Promise<void>` — **ไม่ส่งค่าที่เพิ่งเขียนกลับมา**

บรรทัดถัดมาจึงส่งต่อ `{ ...order, shareStatus: status }` ซึ่งเป็นใบ**ก่อน**การเขียน
`sentAt` ที่อัปเดตแล้วไม่ได้ติดไปด้วย

`needsResend()` ใน `src/services/purchaseOrders.ts:470` ตัดสินจาก `sentAt`:

```ts
return order.shareStatus === 'sent' && (order.sentAt ?? 0) < last.at
```

`sentAt` ที่ค้างอยู่เป็นเวลา**ก่อน**การแก้ไข ซึ่งน้อยกว่าเวลาของ revision ล่าสุดเสมอ
ป้ายจึงยังขึ้นว่าต้องส่งใหม่ จนกว่าจะโหลดใบจากฐานข้อมูลอีกครั้ง

ฐานข้อมูลถูกต้องมาตลอด — ผิดเฉพาะสำเนาที่หน้าจอถืออยู่

## ผลข้างเคียงที่ยังไม่ได้ตรวจ

ตัวกรองสถานะของหน้านี้ใช้ `needsResend` ด้วย (`src/pages/Orders.tsx:180-181`)
แท็บ "ส่งเข้า LINE แล้ว" กับ "ยังไม่ได้ส่ง LINE" จึงน่าจะนับใบนี้ผิดข้างในจังหวะเดียวกัน
**ต้องตรวจตอนแก้** ไม่ใช่ตอนนี้

## ทำไมจึงจัดเป็น BUG / severity major / risk MEDIUM

**BUG ไม่ใช่ UX_FRICTION** — ต่างจาก UX-0003 และ UX-0004 ตรงที่เรื่องนี้ระบบไม่ได้ทำถูกแล้วสื่อสารไม่ดี
แต่หน้าจอ**แสดงค่าที่ผิด** ค่าที่ถูกมีอยู่แล้วในฐานข้อมูล

**severity major** เพราะข้อมูลที่ผิดคือ "ผู้ขายรู้เรื่องการแก้หรือยัง" ซึ่งเป็นคำถามที่ persona ของหัวหน้า
ระบุว่าเป็นสิ่งที่กังวลโดยตรง คนที่เชื่อป้ายจะส่งซ้ำให้ผู้ขายโดยไม่จำเป็น หรือแย่กว่านั้นคือเลิกเชื่อป้ายทั้งหมด
ไม่ถึง `blocker` เพราะงานเดินต่อได้

**risk MEDIUM** — การแก้อยู่ที่สำเนาบนหน้าจอ ไม่ใช่ที่สิ่งที่เขียนลงเอกสาร
**ห้าม patch เปลี่ยนสิ่งที่ `setShareStatus` เขียนลงฐานข้อมูล** ถ้าทางแก้ไหนไปแตะตรงนั้น ต้องยกเป็น `HIGH`
เพราะเข้าเขต "การออกใบสั่งซื้อ" ตามตารางใน README

## regression test ที่ควรมีคู่กับการแก้

`needsResend()` เป็นฟังก์ชัน pure อยู่แล้ว เขียนเทสต์ได้ตรง ๆ ว่าใบที่เพิ่งถูกบันทึกว่าส่งแล้ว
หลังการแก้ไข ต้องได้ `false` — เทสต์นี้ต้องล้มก่อนแก้และผ่านหลังแก้
