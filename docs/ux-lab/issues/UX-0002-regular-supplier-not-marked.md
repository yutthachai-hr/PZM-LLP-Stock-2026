# ผลค้นหามีของชื่อเดียวกันสี่แถว ไม่มีอะไรบอกว่าเจ้าไหนคือเจ้าประจำ

## อาการ

พิมพ์ `rocket` ในช่องเพิ่มสินค้าของหน้าสร้างใบขอซื้อ ได้ผลสี่แถวที่ชื่อเหมือนกันหมด ต่างกันแค่วงเล็บท้ายชื่อ:

```
ROCKET SALAD (ACK)          VGT-01-03-001  KG  ACK
ROCKET SALAD (KIN-D)        VGT-01-03-002  KG  KIN-D
ROCKET SALAD (SIMUNMMANG)   VGT-01-03-004  KG  SIMMUMMUANG
ROCKET SALAD (YC)           VGT-01-03-003  KG  YC
```

แต่ละแถวบอกรหัสผู้ขายไว้แล้ว แต่**ไม่มีแถวไหนถูกทำเครื่องหมายว่าเป็นเจ้าที่ร้านสั่งประจำ**
ป้าย **"ACK (ผู้ขายประจำ)"** โผล่ในช่องผู้ขาย**หลังจากกดเลือกไปแล้ว**เท่านั้น

พนักงานสาขาไม่รู้จักตัวย่อพวกนี้เลย — persona ระบุไว้ว่าไม่รู้ว่าของมาจากผู้ขายเจ้าไหน

## ที่คาดว่าจะเป็น

เห็นตั้งแต่ในรายการว่าแถวไหนคือของที่ร้านสั่งอยู่เป็นประจำ แล้วกดแถวนั้นได้เลย
โดยไม่ต้องกดเข้าไปดูก่อนแล้วค่อยรู้ว่าเดาถูกหรือเปล่า

## ทำซ้ำได้โดย

1. เข้าเดโม เลือกแบรนด์ Pizza Mania
2. ไปหน้ารายการขอสั่งซื้อ แล้วกด "สร้างรายการขอสั่งซื้อ"
3. พิมพ์ `rocket` ในช่อง "ค้นหาชื่อสินค้า / รหัสสินค้า"

ได้สี่แถวตามด้านบน ไม่มีเครื่องหมายใดแยกเจ้าประจำออกจากเจ้าอื่น
กดแถวแรก → ช่องผู้ขายขึ้น "ACK (ผู้ขายประจำ)" ซึ่งเป็นข้อมูลที่ควรเห็นก่อนกด ไม่ใช่หลังกด

แต่ run แรกไปไม่ถึงขั้นเลือก จึงไม่นับเป็นหลักฐานของเรื่องนี้

`route` จึงเป็น `*` ไม่ใช่หน้าใดหน้าหนึ่ง

ที่หน้ารับของยังหนักกว่าหน้าขอซื้อ เพราะ**เลือกผิดเจ้าแปลว่ายอดคงเหลือของสินค้าผิดตัวถูกเพิ่ม**
ซึ่งเป็นข้อมูลที่แก้ย้อนหลังได้แต่ต้องรู้ตัวก่อนว่าผิด

## คำถามที่ยังไม่มีคำตอบ ต้องตอบก่อนแก้

**แถว ACK มาก่อนเพราะเป็นเจ้าประจำ หรือเพราะเรียงตามตัวอักษร?** ในตัวอย่างนี้ ACK เป็นทั้งสองอย่างพร้อมกัน
จึงแยกไม่ออกจากเคสเดียว ถ้าเรียงตามตัวอักษรล้วน แปลว่าสินค้าที่เจ้าประจำขึ้นต้นด้วยตัวท้าย ๆ
จะถูกดันลงไปอยู่ล่างสุด และการ "เดาแถวบนสุด" จะพาไปผิดเจ้า — นั่นจะทำให้เรื่องนี้แรงกว่าที่ประเมินไว้

หาคำตอบตอนขั้น `FIXING` ไม่ใช่ตอนนี้

## ทำไมจึงจัดเป็น UX_FRICTION / severity major / risk MEDIUM

**UX_FRICTION ไม่ใช่ BUG** — ระบบแสดงข้อมูลถูกต้องครบถ้วน สี่แถวคือสินค้าสี่รายการจริง ๆ ในแคตตาล็อก
สิ่งที่ขาดคือการชี้ว่าแถวไหนคือคำตอบที่ถูกสำหรับคนที่ไม่รู้จักผู้ขาย

**ไม่ใช่ BUSINESS_RULE** — การที่ผักตัวเดียวมีสี่ผู้ขายเป็นเรื่องจริงของบริษัท ไม่ใช่กติกาที่ตั้งผิด

**severity major ไม่ใช่ blocker** เพราะ run ที่สองผ่านไปได้ แต่ผ่านด้วยการเดา — ถ้าเดาผิดจะได้ใบขอซื้อที่สั่งผิดเจ้า
ซึ่งไปโผล่เป็นงานของหัวหน้าให้ต้องแก้ทีหลัง

**risk MEDIUM** เพราะการแก้อยู่ในขอบเขตการแสดงผลของรายการค้นหา ไม่เปลี่ยนการผูกผู้ขาย จำนวน หรือการอนุมัติ
**ถ้าทางแก้กลายเป็นการเปลี่ยนว่าสินค้าผูกกับผู้ขายเจ้าไหน ต้องยกเป็น HIGH ทันที** ตามตารางใน README
