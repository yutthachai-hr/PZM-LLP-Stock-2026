# ฟอร์มแก้ไขสินค้าเปิดให้พนักงานและหัวหน้าดูได้ แต่แก้ไม่ได้ บันทึกไม่ได้ และไม่บอกว่าทำไม

## อาการ

พนักงานอยากตั้งจุดสั่งซื้อของชีสไว้ที่ 5 กิโล กดชื่อสินค้า ได้หน้าต่าง **"แก้ไขสินค้า"**
ในนั้นมีช่อง **"สต๊อกขั้นต่ำ (แจ้งเตือนเมื่อถึง)"** ซึ่งตรงกับสิ่งที่ต้องการพอดี

ล่างสุดของหน้าต่างมีปุ่มเดียวคือ **"ปิด"** ไม่มีปุ่มบันทึก
มี "บันทึกราคาใหม่" อยู่ในส่วนต้นทุน แต่เป็นคนละเรื่องและกดไม่ได้

พนักงานลองสี่ทาง — กดชื่อสินค้า, เมนู ⋮ ท้ายแถว, มุมมองการ์ด, ปิดด้วย X กับปิดด้วยปุ่ม —
ได้หน้าต่างเดียวกันทุกทาง แล้วยอมแพ้

## ตรวจแล้ว: หนักกว่าที่รายงาน

ตรวจ DOM ตอนล็อกอินเป็นพนักงาน: **ทุกช่องในฟอร์มมี `disabled = true`** ไม่ใช่แค่ไม่มีปุ่มบันทึก
ปุ่มที่มีทั้งหน้าต่างคือ `บันทึกราคาใหม่` (จาง กดไม่ได้) กับ `ปิด`

ต้นเหตุอยู่ที่ `src/pages/Products.tsx:541` ซึ่งส่ง `canEdit={isAdmin}`
ทุก input ใน `ProductEditor.tsx` ผูกกับ `disabled={!canEdit}` และปุ่มบันทึกอยู่ใต้ `{canEdit && ...}`

**แปลว่าหัวหน้าก็แก้ไม่ได้เหมือนกัน** ไม่ใช่แค่พนักงาน

## สิ่งที่ผิดไม่ใช่เรื่องสิทธิ์ แต่คือความเงียบ

การจำกัดให้แอดมินแก้ข้อมูลหลักของสินค้าเป็นการตัดสินใจที่สมเหตุสมผล
และฝั่ง Firestore ก็ยอมให้ staff แก้ได้แค่ `unitConversions` อยู่แล้ว — **ห้ามแก้เรื่องสิทธิ์จาก Issue นี้**

สิ่งที่ผิดคือหน้าต่างชื่อ **"แก้ไขสินค้า"** เปิดขึ้นมาเต็มรูปแบบให้คนที่แก้ไม่ได้
โดยไม่มีข้อความสักคำว่าเป็นแบบอ่านอย่างเดียว หรือว่าต้องไปบอกใครถ้าอยากให้แก้

พนักงานจึงใช้เวลาไปกับการหาปุ่มที่ไม่มีวันมี แล้วสรุปว่าตัวเองทำไม่เป็น

## ทำซ้ำได้โดย

1. เข้าเดโม ล็อกอินเป็น `staff@inventory-pzm.local` เลือกแบรนด์ Pizza Mania
2. ไปหน้า "สินค้าคงคลัง" กดที่ชื่อสินค้าแถวใดก็ได้
3. เลื่อนหน้าต่างลงจนสุด

ล่างสุดมีปุ่ม "ปิด" ปุ่มเดียว · ทุกช่องกรอกไม่ได้ · ไม่มีข้อความอธิบาย

ทำซ้ำกับ `manager@inventory-pzm.local` ได้ผลเหมือนกัน

## ที่ agent รายงานคลาดเคลื่อน

agent เขียนว่าพิมพ์ 5 ลงช่องแล้วเห็นเลขเปลี่ยนเป็น 5 จริง — **ข้อนั้นเป็นไปไม่ได้ เพราะช่องถูก disabled**
น่าจะจำสลับกับช่องอื่นหรืออ่านผิด

แต่ข้อสรุปหลักถูก และสาเหตุจริงแย่กว่าที่มันคิด: ไม่ใช่ "ลืมใส่ปุ่มบันทึก" แต่เป็น
"เปิดฟอร์มอ่านอย่างเดียวโดยไม่บอก"

## ทำไมจึงจัดเป็น UX_FRICTION / severity blocker / risk LOW

**ไม่ใช่ BUG** — ระบบทำตามสิทธิ์ที่ตั้งใจไว้ทุกประการ

**severity blocker** เพราะงานที่ตั้งใจทำ (ตั้งจุดสั่งซื้อ) **ทำไม่ได้เลยด้วยเส้นทางใด ๆ**
และ run นี้จบด้วยการยอมแพ้จริง ๆ ไม่ใช่แค่เสียเวลา

**risk LOW** เพราะทางแก้คือข้อความ — บอกว่าอ่านอย่างเดียว บอกว่าต้องให้แอดมินแก้
**ห้ามแก้ด้วยการเปิดสิทธิ์ให้พนักงานหรือหัวหน้าแก้สินค้าได้** นั่นเป็นการเปลี่ยนกติกา
ต้องให้เจ้าของตัดสิน และจะกลายเป็น `HIGH` ทันที

## คำถามที่เจ้าของควรตอบ เพราะเปลี่ยนรูปของทางแก้

**หัวหน้าควรตั้งจุดสั่งซื้อเองได้ไหม?**

ถ้าควร — นี่ไม่ใช่เรื่องถ้อยคำอีกต่อไป แต่เป็นการเปลี่ยนสิทธิ์ ซึ่งต้องแก้ทั้ง `canEdit` และ firestore.rules
ถ้าไม่ควร — ทางแก้คือข้อความอย่างเดียว และเรื่องนี้ปิดได้เร็ว

ระหว่างนี้ยังไม่มีใครแตะโค้ด
