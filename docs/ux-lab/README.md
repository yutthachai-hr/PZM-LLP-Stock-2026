# UX Lab

เจ้าของระบบเป็นตัวกลางระหว่างพนักงานที่ติดอยู่หน้าจอ กับคนที่แก้หน้าจอนั้นได้ พนักงานบ่นให้ฟัง
เจ้าของแปลเป็นคำสั่ง คนแก้แก้ แล้ววนใหม่ ที่นี่คือการเอาตัวกลางนั้นออก — ให้การใช้งานจริงกลายเป็นหลักฐาน
หลักฐานกลายเป็นเรื่องที่มีโครงสร้าง และเรื่องนั้นเดินไปจนถึงการแก้ที่พิสูจน์แล้วว่าดีขึ้นจริง

## วงจร

รัน scenario → รายงาน → Issue → reproduce → patch เล็กที่สุด → regression test → ด่าน QA
→ branch `demo` → retest → `VERIFIED` → เจ้าของสั่ง merge → `RELEASED` → `CLOSED`

## เส้นที่ห้ามข้าม

**ทุกอย่างวิ่งบน `npm run demo` เท่านั้น** — ไม่มีขั้นตอนไหนในวงจรนี้แตะ `pzm-stock-x5` ได้
เดโมไม่มี Firebase config เลย (`src/backend/index.ts` จึงตกไปใช้ `createLocalBackend()`) ข้อมูลอยู่ในเบราว์เซอร์ล้วน

**reproduce ไม่ได้ ห้ามแก้โค้ดแบบเดา** — ลง `NEEDS_MORE_DATA` แล้วรัน scenario เพิ่มเพื่อเก็บข้อมูล
การแก้โค้ดตามอาการที่ยังทำซ้ำไม่ได้ คือการเพิ่มโค้ดที่ไม่มีใครรู้ว่าแก้อะไร

**ห้าม push `main` ห้าม deploy** — เจ้าของเป็นคนสั่งเท่านั้น

## Risk

`risk` ตอบคำถามว่า **การแก้ตรงนี้อันตรายแค่ไหน**

| Risk | ตัวอย่าง | ทำได้ถึงไหน |
|---|---|---|
| `LOW` | ระยะห่าง, ถ้อยคำ, responsive, layout | แก้ + ทดสอบ + ลง branch `demo` ได้เอง |
| `MEDIUM` | ค้นหา, ตัวกรอง, validation, การกรอกฟอร์ม | เท่าข้างบน + ต้อง retest scenario เดิมให้ผ่านก่อน |
| `HIGH` | ผู้ขาย, จำนวนที่อนุมัติ, สถานะอนุมัติ, การออกใบสั่งซื้อ | สร้าง patch ได้ แต่**ขึ้น `main` ต้องเจ้าของอนุมัติ** |
| `CRITICAL` | จำนวนสต๊อก, มูลค่า, migration ที่ทำลายข้อมูล, auth/security | **ห้ามขึ้นอัตโนมัติเด็ดขาด** |

ข้อนี้ไม่ได้อาศัยความจำของใคร — `validateLedger` ใน `scripts/ux-lab/ledger.ts` จะปฏิเสธทะเบียน
ที่บอกว่าเรื่องระดับ `HIGH` หรือ `CRITICAL` ขึ้นของจริงไปแล้วโดยไม่มี `ownerApproved` และมีเทสต์คุมอยู่

## Severity ไม่ใช่ Risk

`severity` ตอบคนละคำถาม — **ปัญหานี้ขวางงานแค่ไหน**: `blocker` ทำงานต่อไม่ได้เลย · `major` ทำได้แต่เสียเวลามาก
· `minor` รำคาญ · `cosmetic` แค่ไม่สวย

ปุ่มเบี้ยวในหน้าอนุมัติมี severity ต่ำ แต่ risk สูง `severity` ใช้จัดลำดับว่าแก้อะไรก่อน `risk` ใช้ตัดสินว่าทำเองได้ถึงไหน

## Category

| Category | ความหมาย |
|---|---|
| `BUG` | ระบบทำงานไม่ตรงกับที่ตัวเองสัญญาไว้ |
| `UX_FRICTION` | ระบบทำงานถูก แต่กว่าจะถึงปลายทางเสียแรงเกินจำเป็น |
| `MISSING_FEATURE` | สิ่งที่งานจริงต้องการ แต่ระบบยังไม่มี |
| `BUSINESS_RULE` | ระบบทำตามกติกา แต่กติกานั้นไม่ตรงกับที่บริษัททำจริง |
| `TRAINING_ISSUE` | ระบบถูก คนไม่เข้าใจ |
| `PERFORMANCE` | ช้าจนเปลี่ยนวิธีทำงานของคน |

**`TRAINING_ISSUE` = ระบบถูกแต่คนไม่เข้าใจ → ห้ามแก้โค้ด เสนอได้แค่เปลี่ยนถ้อยคำ**
ถ้าเจอ `TRAINING_ISSUE` ซ้ำ ๆ ที่หน้าเดียวกันหลาย run นั่นแปลว่าถ้อยคำผิด ไม่ใช่คนโง่ — ยกเป็น `UX_FRICTION` ได้

## การรวมปัญหาซ้ำ

`dedupeKey` ในโค้ดคือ `route|category` ซึ่งพอใช้ได้กับเรื่องที่อยู่หน้าเดียว
แต่ **เรื่องที่มีต้นเหตุเดียวกันแล้วโผล่หลายหน้า ต้องเป็น Issue ใบเดียว ไม่ใช่ใบต่อหน้า**
เพราะการแก้ครั้งเดียวจะดับทุกหน้าพร้อมกัน — แตกเป็นหลายใบคือการนับปัญหาเดียวซ้ำ ๆ แล้วทำให้ลำดับความสำคัญเพี้ยน

Issue แบบนั้นใส่ `route: "*"` และเขียนไว้ในตัวไฟล์ว่าเจอที่หน้าไหนบ้าง
(บทเรียนจาก 23 ก.ย. — การค้นหาด้วยชื่อไทยไม่เจอ โผล่ที่ `/requests`, `/receive` และหน้าตรวจใบขอซื้อ
ทั้งหมดมาจากเหตุเดียวคือแคตตาล็อกเป็นภาษาอังกฤษล้วน)

ตรงข้าม: ถ้าอาการเหมือนกันแต่**ต้นเหตุคนละตัว** ให้แยกใบ เช่น "ค้นไม่เจอ" กับ "ค้นไม่เจอแล้วไม่บอกว่าไม่เจอ"
เป็นคนละเรื่อง แก้คนละที่

## State

```
NEW                   → ANALYZING
ANALYZING             → REPRODUCED | NEEDS_MORE_DATA | CLOSED
NEEDS_MORE_DATA       → ANALYZING
REPRODUCED            → FIXING
FIXING                → QA_PASSED | QA_FAILED
QA_FAILED             → FIXING
QA_PASSED             → READY_FOR_USER_RETEST
READY_FOR_USER_RETEST → VERIFIED | ANALYZING
VERIFIED              → READY_FOR_RELEASE
READY_FOR_RELEASE     → RELEASED
RELEASED              → CLOSED
CLOSED                → (จบ)
```

`ANALYZING → CLOSED` มีไว้สำหรับเรื่องที่วิเคราะห์แล้วพบว่าไม่ต้องแก้โค้ด เช่น `TRAINING_ISSUE`
`READY_FOR_USER_RETEST → ANALYZING` คือ retest แล้วยังติด — ย้อนกลับไปที่การคิด ไม่ใช่ที่การแก้

## ชื่อโฟลเดอร์ของ run

```
YYYY-MM-DD-SC-0NN-<persona>-<viewport>
```

`viewport` เป็น `desktop` หรือ `mobile` เท่านั้น การ retest เติม `-retest` ต่อท้าย

## วิธีรัน

1. เปิดสนามซ้อม: `npm run demo` แล้วเปิด `http://localhost:5175`
2. **กด "รีเซ็ตข้อมูลเดโม" ที่ต้นสายเท่านั้น ไม่ใช่ก่อนทุก run** (ดูหัวข้อ "สายของ scenario" ด้านล่าง)
   บัญชีเดโม: `demo@inventory-pzm.local` (แอดมิน) · `manager@inventory-pzm.local` (หัวหน้า)
   · `staff@inventory-pzm.local` (พนักงาน) รหัสเดียวกันหมด `demo1234` — แสดงอยู่ในหน้าเข้าสู่ระบบของเดโมเอง
3. ตั้งขนาดจอ: `desktop` = 1440×900, `mobile` = 375×812
4. อ่าน persona แล้วอ่าน scenario — **แล้วปิดสเปกทิ้ง** ห้ามเปิดโค้ดหรือเอกสารอื่นระหว่างรัน
5. ทำงานให้บรรลุเป้าหมาย จับเวลาตั้งแต่คลิกแรกหลังเข้าสู่ระบบ
6. ดูหน้าจอทุกครั้งที่ติด แล้วบรรยายไว้ให้ละเอียด
7. เขียน `report.md` จาก `runs/TEMPLATE.md`

**สองข้อจำกัดที่รู้แล้วจากการรันจริง (23 ก.ย.)**

- **subagent เขียนไฟล์เองไม่ได้** — harness บังคับให้มันคืนผลเป็นข้อความ ดังนั้น agent เขียนรายงานเป็นข้อความ
  แล้ว**เจ้าของ session เป็นคนบันทึกลงไฟล์ให้ตามที่มันเขียนมา ห้ามแก้เนื้อความ** เพราะรายงานคือสิ่งที่เกิดกับมัน
- **บันทึกภาพหน้าจอเป็นไฟล์ไม่ได้** — เครื่องมือเบราว์เซอร์คืนภาพให้ดูตอนนั้น แต่ไม่มีทาง export เป็นไฟล์
  หลักฐานของ run จึงเป็น**คำบรรยายกับตัวเลข** และชดเชยด้วยกติกาที่เข้มกว่าเดิม: **ทุกจุดที่ติดต้องถูกทำซ้ำโดยฝั่ง dev เอง
  ก่อนตั้งเป็น Issue เสมอ** ถ้าทำซ้ำไม่ได้ ไม่ตั้ง — ดู `runs/2026-09-23-SC-001-staff-branch-desktop/dev-note.md`
  ที่คัดปัญหาปลอมออกไป 3 ใน 4 ข้อ

**ก่อนเริ่มกวาดทุกครั้ง ต้องยืนยันว่าสนามซ้อมมีข้อมูลที่ scenario ต้องใช้จริง** — สินค้า คลัง ผู้ขาย ยอดคงเหลือ
ถ้าข้อมูลขาด สิ่งที่วัดได้คือความว่างเปล่าของข้อมูล ไม่ใช่ความเข้าใจง่ายของหน้าจอ
(บทเรียนจาก run แรก 23 ก.ย. — เดโมไม่มีผู้ขายเลยสักเจ้า ทุกหน้าสั่งซื้อจึงตัน ดู `runs/2026-09-23-SC-001-staff-branch-desktop/dev-note.md`)

**ห้ามแก้ไฟล์ใน `src/` ระหว่างที่ยังมี run ค้างอยู่** — เดโมรันบน Vite ซึ่งจะรีโหลดหน้าจอทันทีที่ไฟล์เปลี่ยน
agent ที่กำลังทำงานอยู่จะโดนดึงพรมออกจากใต้เท้ากลางคัน run นั้นใช้ไม่ได้ทั้ง run
การแก้ Issue จึงต้องรอให้กวาดจบก่อนเสมอ ไม่ใช่แก้แทรกระหว่างทาง

**ถ้าระหว่างรันเผลอไปอ่านโค้ดเพื่อหาว่าปุ่มอยู่ไหน ให้ทิ้ง run นั้นแล้วเริ่มใหม่ — run นั้นใช้ไม่ได้แล้ว**
เพราะสิ่งที่วัดอยู่คือ "หน้าจอบอกทางได้เองไหม" ไม่ใช่ "คนที่รู้คำตอบอยู่แล้วทำได้ไหม"

## สายของ scenario

งานจริงไม่ได้เริ่มจากศูนย์ทุกครั้ง หัวหน้าอนุมัติ**ใบที่ลูกน้องเพิ่งส่งมา** และคนที่ตามหาของหาย
ตามจาก**ประวัติที่เกิดขึ้นเมื่อวาน** ถ้ารีเซ็ตก่อนทุก run สิ่งที่วัดได้คือหน้าจอเปล่า ไม่ใช่งานจริง
scenario จึงจัดเป็นสาย **รีเซ็ตที่ต้นสายเท่านั้น แล้วเดินต่อจากของที่ run ก่อนหน้าทิ้งไว้**

| สาย | ลำดับ | ต้นสายรีเซ็ต |
|---|---|---|
| A — สั่งซื้อ | SC-001 → SC-002 → SC-015 | ก่อน SC-001 |
| B — ของเข้าออก | SC-003 → SC-004 → SC-005 → SC-006 → SC-007 → SC-008 | ก่อน SC-003 |
| C — งานตั้งค่าและงานเดี่ยว | SC-009 → SC-010 → SC-011 → SC-012 → SC-013 → SC-014 → SC-016 | ก่อน SC-009 |

SC-007 (ตามหาของหาย) กับ SC-008 (รายงานการใช้) **ต้องอยู่ท้ายสาย B** เพราะทั้งคู่อ่านประวัติที่ SC-003–SC-005 สร้างไว้
SC-002 ต้องมีใบขอซื้อจาก SC-001 และ SC-015 ต้องมีใบสั่งซื้อจาก SC-002

ทุก run ต้องเขียนไว้ใน `## เกิดอะไรขึ้นจริง` ว่าเริ่มจากสภาพไหน — รีเซ็ตใหม่ หรือรับช่วงต่อจาก run ไหน
