# คำตัดสินหลัง reproduce

เขียนโดยฝั่ง dev หลังอ่าน `report.md` แล้วลองทำซ้ำเองในเดโม **ไม่แก้รายงานของ agent**

| จุดที่ติด | ผล reproduce | เป็น Issue ไหม |
|---|---|---|
| 1. ค้นหาชื่อไทยไม่เจอ | **REPRODUCED** (เฉพาะส่วนภาษาไทย) | นับเข้า `UX-0001` เป็น run ที่สาม |
| 1ก. "coke zero" ภาษาอังกฤษก็ไม่เจอ | **NOT_REPRODUCED — เป็นเท็จ** | ไม่ |
| 2. ใบสั่งซื้อสองใบได้เลข PO-00001 เหมือนกัน | **REPRODUCED** | ใช่ → `UX-0003` |
| 3. กด Excel แล้วไม่มีอะไรยืนยัน | **REPRODUCED** | ใช่ → `UX-0004` |

## ข้อ 1ก ไม่จริง

agent เขียนว่าพิมพ์ `coke zero` เป็นภาษาอังกฤษแล้วยังไม่เจอ ต้องพิมพ์ `zero` คำเดียวถึงเจอ

ลองเองแล้ว: พิมพ์ `coke zero` ในช่อง "ค้นหาชื่อสินค้า / รหัสสินค้า" ของหน้าสร้างใบขอซื้อ
**เจอทันที** — `COKE ZERO CAN 325 ML 1X24 (THAINAMTHIP)` / `BEV-01-01-004` / Pack / THAINAMTHIP

โค้ดก็ยืนยัน: `looseIncludes` ใน `src/lib/search.ts` ตัดช่องว่างทิ้งทั้งสองฝั่งก่อนเทียบ
`"cokezero"` จึงอยู่ใน `"cokezerocan325ml1x24thainamthip"` ตรง ๆ

สาเหตุที่น่าจะเป็นไปได้ที่สุดคือ agent พิมพ์ทับโดยข้อความภาษาไทยเดิมยังค้างอยู่ในช่อง
ทำให้ค่าจริงในช่องเป็น `โค้กcoke zero` ซึ่งหาไม่เจอแน่นอน — เป็นความผิดพลาดของตัวมันเอง ไม่ใช่ของระบบ

**นี่คือตัวอย่างว่าทำไมด่าน reproduce ต้องมี** ถ้าเชื่อตามรายงาน จะได้ Issue ว่า "ค้นหาหลายคำไม่ทำงาน"
แล้วมีคนไปแก้ตัวจับคู่ที่ไม่ได้พัง

## ข้อ 2 จริง แต่ระบบทำถูก

เห็นกับตา: ตารางหน้า `/orders` มีสองแถว `ACK · PO-00001` และ `THAINAMTHIP · PO-00001`

**เลข PO รันแยกตามผู้ขายเป็นการตัดสินใจของเจ้าของเมื่อ 14 ก.ย. 2569** (`counters/purchaseOrder__<supplierId>`)
ผู้ขายแต่ละเจ้าเห็นเลขของตัวเองเรียง 1, 2, 3 ซึ่งเป็นสิ่งที่ผู้ขายต้องการ
เลขจึงซ้ำข้ามผู้ขายโดยตั้งใจ ไม่ใช่บั๊ก

สิ่งที่ผิดคือหน้าจอไม่ได้บอกเรื่องนี้เลย หัวหน้าเห็นสองแถวเลขเดียวกันติดกันแล้วนึกว่าระบบพัง
จึงเป็น `UX_FRICTION` ของการแสดงผล ไม่ใช่ `BUG` และไม่ใช่ `BUSINESS_RULE`

**ห้ามแก้ด้วยการเปลี่ยนวิธีออกเลข** — นั่นขัดกับการตัดสินใจของเจ้าของ ทำให้ใบที่พิมพ์ส่งผู้ขายไปแล้วเพี้ยน
และเป็นงานระดับ `HIGH` ที่ต้องให้เจ้าของอนุมัติ ทางแก้ที่ถูกอยู่ที่การแสดงผลเท่านั้น

## ข้อ 3 จริง และยืนยันในโค้ดแล้ว
