## ตรวจ DOM แล้วได้ภาพที่ชัดกว่าที่ agent เห็น

ล็อกอินเป็นพนักงาน เปิดหน้าต่าง "แก้ไขสินค้า" แล้วตรวจ:

- ช่องกรอกในฟอร์ม **`disabled = true`**
- ปุ่มทั้งหมดในหน้าต่าง: `บันทึกราคาใหม่` (จาง กดไม่ได้) และ `ปิด` — **ไม่มีปุ่มบันทึก**

ต้นเหตุ: `src/pages/Products.tsx:541` ส่ง `canEdit={isAdmin}`
ใน `src/pages/products/ProductEditor.tsx` ทุก input ผูกกับ `disabled={!canEdit}`
และปุ่มบันทึกอยู่ใต้เงื่อนไข `{canEdit && ...}` (บรรทัด 534–536)

**แปลว่าหัวหน้าก็เจอแบบเดียวกัน** ไม่ใช่แค่พนักงาน

## ทำไมข้อสรุปจึงต่างจากที่ agent เขียน

agent สรุปว่า "ลืมใส่ปุ่มบันทึก" ซึ่งฟังดูเหมือนงานเล็ก
ของจริงคือ **"เปิดฟอร์มอ่านอย่างเดียวโดยไม่บอกใครว่าอ่านอย่างเดียว"** ซึ่งเป็นคนละปัญหาและใหญ่กว่า

ถ้าเชื่อตามรายงานแล้วไป "เพิ่มปุ่มบันทึก" ให้ ก็จะกลายเป็นการเปิดสิทธิ์ให้พนักงานแก้ข้อมูลหลักของสินค้า
โดยไม่มีใครตัดสินใจเรื่องนั้น — **ซึ่งเป็นการเปลี่ยนกติกา ไม่ใช่การแก้บั๊ก**

## ที่ agent รายงานคลาดเคลื่อน

"ลบให้หมดแล้วพิมพ์ 5 เข้าไป เห็นในช่องเปลี่ยนเป็น 5 จริง" — เป็นไปไม่ได้ เพราะช่องถูก disabled
น่าจะจำสลับกับช่องอื่น หรือเห็นเป็นค่าที่ตัวเองตั้งใจจะใส่

ข้อนี้ไม่กระทบข้อสรุป เพราะปลายทางเหมือนกันคือบันทึกไม่ได้ — แต่บันทึกไว้เพื่อความตรงไปตรงมา

## เรื่องที่ agent ยกไว้ในข้อสังเกต และมีน้ำหนักจริง

*"คอลัมน์จุดสั่งซื้อของทุกตัวเป็น 0 หมด ... แปลว่า 'สินค้าใกล้หมด 0 รายการ' อาจไม่ได้แปลว่าของไม่ขาด
แต่เป็นเพราะยังไม่มีใครตั้งเกณฑ์ขั้นต่ำให้สินค้าตัวไหนเลย"*

ข้อนี้ถูกต้อง และ agent เลือกไม่ตั้งเป็นเรื่องเพราะ "หน้าจอบอกข้อมูลตรงตามที่มีจริง" ซึ่งก็ถูกอีก

**แต่มันเชื่อมกับ `UX-0011` โดยตรง**: ระบบเตือนของใกล้หมดไม่ได้ถ้าไม่มีใครตั้งขั้นต่ำ
และคนที่อยากตั้งขั้นต่ำ — ทั้งพนักงานและหัวหน้า — ตั้งไม่ได้
ความสามารถทั้งชุดจึงขึ้นกับการที่แอดมินไปตั้งให้ทีละตัวจาก 288 รายการ

นี่เป็นข้อมูลที่เจ้าของควรรู้ตอนตัดสินใจเรื่องสิทธิ์ใน `UX-0011` จึงเขียนไว้ที่นี่ ไม่ตั้งเป็นเรื่องแยก

## ผลข้างเคียง: ต้องแก้ Issue ที่เขียนไปแล้ว

`UX-0010` เคยเขียนไว้ว่าพนักงานอาจ "เผลอแก้ข้อมูลโดยไม่ตั้งใจ" — **ข้อนั้นไม่จริง** ช่องถูก disabled อยู่แล้ว
แก้ข้อความใน `UX-0010` เรียบร้อยแล้ว ความเสี่ยงที่แท้จริงคือการเสียเวลา ไม่ใช่ข้อมูลเสียหาย
