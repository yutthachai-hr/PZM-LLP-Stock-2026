## 1. ปัญหาที่กำลังแก้

เจ้าของเป็นตัวกลางระหว่างพนักงานกับ dev ตลอดเวลา พนักงานบ่นให้ฟัง เจ้าของแปลเป็นคำสั่ง dev แก้ แล้ววนใหม่
เป้าหมายคือให้ **การใช้งานจริง → หลักฐาน → Issue ที่มีโครงสร้าง → reproduce → patch เล็กที่สุด → test → สนามซ้อม → ลองใหม่ → ยืนยันว่าดีขึ้น** เดินได้เองโดยไม่ต้องมีเจ้าของคั่นทุกขั้น

**ทางแยกที่ตัดสินไปแล้ว (23 ก.ย.)**: เริ่มด้วย **agent สวมบทพนักงาน/หัวหน้า** ก่อน แล้วค่อยเปิดให้คนจริงใช้ทีหลัง
เหตุผลคือ agent เล่าได้ว่าตัวเองงงตรงไหน — คนจริงเล่าไม่ได้ จึงต้องมี telemetry ซึ่งเป็นงานอีกก้อน (โครง 4–6)

**กติกาที่อยู่เหนือทุกอย่าง** มาจากสเปกของเจ้าของ: *"อย่าบังคับ User ทำตาม step UI ให้บอก Goal ของงาน เพื่อให้เห็นว่า UX เข้าใจง่ายจริงหรือไม่"*
ข้อนี้ตัดวิธีเขียนสคริปต์ทางเดินล่วงหน้าทิ้งทั้งหมด สคริปต์รู้ทางอยู่แล้ว มันจะไม่มีวันหาปุ่มไม่เจอ ซึ่งคือปัญหาที่เราอยากเห็นที่สุด

## 4. Persona

Persona ไม่ได้บอกแค่ว่าเป็นใคร แต่บอกว่า **ไม่รู้อะไร** — นี่คือส่วนที่ทำให้ agent หลงทางได้เหมือนคนจริง

ทุก persona ต้องระบุ: ทำงานอะไร · รู้จักสินค้าด้วยชื่ออะไร · ใช้เครื่องอะไร · ไม่เคยอ่านคู่มือ · ไม่รู้รหัส SKU
· ไม่รู้ว่าเมนูไหนทำอะไรจนกว่าจะกดเข้าไปดู · ภาษาที่ใช้คิดคือภาษาไทย

**`staff-branch`** — พนักงานสาขา เรียกของด้วยชื่อเล่น ("ผักร็อกเก็ต" ไม่ใช่ `VGT-01-03-002`) ไม่รู้ว่าของมาจากผู้ขายเจ้าไหน
งานประจำคือรับของ เบิกของ นับสต๊อก และขอให้สั่งของเพิ่มเมื่อใกล้หมด

**`manager`** — หัวหน้า ดูของที่ลูกน้องขอ ตัดจำนวนลงได้ เพิ่มของที่ลูกน้องลืม อนุมัติ แล้วออกใบสั่งซื้อ
สนใจว่า "ของนี้แพงไปไหม" และ "สั่งซ้ำกับเมื่อวานหรือเปล่า"

## 5. Scenario

เขียนเป็น **เป้าหมาย** เท่านั้น ตัวอย่าง:

> **SC-001** พรุ่งนี้ผักจะหมด ขอให้สั่ง ROCKET SALAD 3 KG กับ RED OAK 5 KG และโค้กกระป๋อง 5 แพ็ค แล้วส่งให้หัวหน้าดู

ทุก scenario ต้องมี: เป้าหมาย · persona ที่ใช้ · ขนาดจอ · **"ถือว่าเสร็จเมื่อไหร่"** (เพื่อแยก *ทำสำเร็จ* ออกจาก *ยอมแพ้*)
**ห้ามเขียนว่าปุ่มอยู่ไหน เมนูชื่ออะไร หรือต้องกดกี่ครั้ง**

รอบแรกครอบ **ทุกหน้าในแอป** (มติเจ้าของ 23 ก.ย.): ภาพรวม · สินค้าคงคลัง · รับเข้า · เบิก/โอนสาขา · ปรับสต๊อก · นับสต๊อก
· ปฏิทินคลัง · Stock Card · รายงาน · ขอสั่งซื้อ · อนุมัติ · ใบสั่งซื้อ · ผู้ขาย · ข้อความภายใน · บาร์โค้ด

## 6. ตัวเลขที่ทุก run ต้องบันทึก

| ตัววัด | ความหมาย |
|---|---|
| completion time | เวลาตั้งแต่เริ่มจนถึงเงื่อนไข "เสร็จ" |
| meaningful actions | จำนวนการกด/พิมพ์ที่มีความหมาย (ไม่นับเลื่อนจอ) |
| search failures | ค้นแล้วไม่เจอของที่ต้องการ กี่ครั้ง |
| validation errors | โดนระบบปฏิเสธ กี่ครั้ง |
| back navigation | กดย้อนกลับ/เปลี่ยนใจ กี่ครั้ง |
| dead ends | ไปถึงหน้าที่ไม่มีทางไปต่อ |
| outcome | `completed` / `completed_with_help` / `abandoned` |

`completed_with_help` = ทำได้แต่ต้องเดาถูกหรือลองผิดหลายครั้ง — ต้องแยกออกจาก `completed` เพราะคนจริงจะยอมแพ้ตรงนั้น

## 7. Issue

ช่องที่ต้องมี: `id` · `title` · `role` · `route/page` · `observed` · `expected` · `steps` · `evidence` (run ไหน ภาพไหน)
· `frequency` (เจอกี่ run) · `affectedScenarios` · `category` · `severity` · `risk` · `state`

**Category** — `BUG` · `UX_FRICTION` · `MISSING_FEATURE` · `BUSINESS_RULE` · `TRAINING_ISSUE` · `PERFORMANCE`

ข้อนี้บังคับใช้กติกาของเจ้าของที่ว่า *"อย่าถือว่า Feedback ทุกอันคือ Bug"*
`TRAINING_ISSUE` = ระบบทำงานถูกแต่คนไม่เข้าใจ → **ห้ามแก้โค้ด** ทำได้แค่เสนอเปลี่ยนถ้อยคำหรือเพิ่มคำอธิบาย

**State machine**

```
NEW → ANALYZING → REPRODUCED ──→ FIXING → QA_PASSED → READY_FOR_USER_RETEST → VERIFIED → READY_FOR_RELEASE → RELEASED → CLOSED
                       │                      │                                    │
                       └→ NEEDS_MORE_DATA     └→ QA_FAILED ──(กลับไป FIXING)        └→ (ยังมีปัญหา) กลับไป ANALYZING
```

**Severity กับ Risk ไม่ใช่ของเดียวกัน** — `severity` = ปัญหานี้ขวางงานแค่ไหน (`blocker` ทำงานต่อไม่ได้เลย / `major` ทำได้แต่เสียเวลามาก
/ `minor` รำคาญ / `cosmetic` แค่ไม่สวย) ส่วน `risk` = การแก้ตรงนี้อันตรายแค่ไหน (§8) ปุ่มเบี้ยวในหน้าอนุมัติมี severity ต่ำแต่ risk สูง
`severity` ใช้จัดลำดับว่าแก้อะไรก่อน `risk` ใช้ตัดสินว่า agent ทำเองได้ถึงไหน

**การรวมปัญหาซ้ำ**: route เดียวกัน + category เดียวกัน + อาการใกล้เคียงกัน = Issue ใบเดียว `frequency` เพิ่มขึ้น
และ**เก็บ evidence ของทุก run ไว้ครบ** ไม่ทับกัน

## 8. เส้นที่ห้ามข้าม

| Risk | ตัวอย่าง | agent ทำได้ถึงไหน |
|---|---|---|
| `LOW` | ระยะห่าง, ถ้อยคำ, responsive, layout | แก้ + ทดสอบ + ลง branch `demo` ได้เอง |
| `MEDIUM` | ค้นหา, ตัวกรอง, validation, การกรอกฟอร์ม | เท่าข้างบน + ต้อง retest scenario เดิมให้ผ่านก่อน |
| `HIGH` | ผู้ขาย, จำนวนที่อนุมัติ, สถานะอนุมัติ, การออก PO | สร้าง patch ได้ แต่**ขึ้น `main` ต้องเจ้าของอนุมัติ** |
| `CRITICAL` | จำนวนสต๊อก, มูลค่า, migration ที่ทำลายข้อมูล, auth/security | **ห้ามขึ้นอัตโนมัติเด็ดขาด** |

**กติกาสามข้อที่ต้องเขียนไว้ใน `docs/ux-lab/README.md` ด้วย:**

1. **ทุกอย่างวิ่งบน `npm run demo` เท่านั้น** ไม่มีขั้นตอนไหนในวงจรนี้แตะ `pzm-stock-x5` ได้ — ตรงกับกติกาเจ้าของ *"อย่าเปลี่ยนแปลงข้อมูลใดใดโดยไม่ถามก่อนเด็ดขาด"*
2. **reproduce ไม่ได้ ห้ามแก้โค้ดแบบเดา** → ลง `NEEDS_MORE_DATA` แล้วรัน scenario เพิ่มเพื่อเก็บข้อมูล
3. **agent ห้าม push `main` ห้าม deploy** ทุกครั้งที่จะขึ้นของจริงต้องผ่านเจ้าของ

## 9. วงจร dev/QA

1. **Reproduce** ใน demo ก่อนเสมอ → `REPRODUCED` / `NOT_REPRODUCED` / `NEEDS_MORE_DATA`
2. **Root cause** หาไฟล์/คอมโพเนนต์/service/state ที่เกี่ยวข้องจริง ๆ
3. **Patch ที่เล็กที่สุด** — ห้าม rewrite ทั้งไฟล์ ห้ามเปลี่ยน business rule (ผู้ขาย จำนวน การอนุมัติ) โดยไม่มีหลักฐานชัดเจน
4. **Regression test** ทุก fix ที่เป็น logic ต้องมี unit test ที่ล้มก่อนแก้และผ่านหลังแก้
   ตัวอย่างจากสเปกเจ้าของ: รายงานว่า *"ค้น red oak แล้วไม่เจอ"* → หลังแก้ต้องมี test ที่ `red oak` / `RED OAK` / `oak` / รหัสสินค้า ได้ผลถูกต้อง
5. **ด่าน QA** (เหมือนด่านก่อน commit ที่ใช้อยู่แล้ว ไม่สร้างใหม่):

```
npx tsc -p tsconfig.app.json --noEmit
npm run lint
npm run i18n:check
npm test                      # 679 unit tests
npm run test:rules            # 166 rules tests
npx tsc -p worker/tsconfig.json --noEmit
npm run build
```

   ล้มข้อใดข้อหนึ่ง = `QA_FAILED` กลับไป `FIXING` **ห้ามข้ามด่าน**
6. **สนามซ้อม** ผ่านด่านแล้ว → branch `demo` → `https://demo.pzmstock.pages.dev` → `READY_FOR_USER_RETEST`
7. **Retest** รัน scenario เดิมด้วย persona เดิมอีกครั้ง เทียบตัวเลข before/after ถ้าดีขึ้นจริง → `VERIFIED` ถ้ายังติด → กลับ `ANALYZING`
8. **ขึ้นของจริง** `VERIFIED → READY_FOR_RELEASE` ทำได้เอง แต่ `READY_FOR_RELEASE → RELEASED` คือการ merge เข้า `main`
   ซึ่ง **เจ้าของเป็นคนสั่งเท่านั้น** (§8 ข้อ 3) หลัง deploy แล้วยืนยันว่าอยู่บนของจริงจึง `CLOSED`

## 11. สิ่งที่ตั้งใจไม่ทำรอบนี้ และเหตุผล

## 12. ถือว่าสำเร็จเมื่อไหร่

1. มี persona 2 ตัวและ scenario ครอบทุกหน้าในแอป เขียนเป็นเป้าหมายล้วน
2. agent รัน scenario บนเดสก์ท็อปครบ แล้วมือถือครบ โดยไม่เคยแตะ `pzm-stock-x5`
3. ทุก run มีรายงานพร้อมตัวเลขทั้งเจ็ดตัวใน §6
4. ปัญหาที่เจอถูกรวมซ้ำแล้วเป็น Issue ที่มี category/severity/risk ครบ อยู่ใน `ledger.json`
5. อย่างน้อยหนึ่ง Issue เดินครบวง `NEW → … → VERIFIED` โดยผ่านด่าน QA ทั้งเจ็ดข้อ
6. ไม่มีอะไรขึ้น `main` โดยที่เจ้าของไม่ได้อนุมัติ
